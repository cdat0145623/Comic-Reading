Tài liệu kỹ thuật

Kiến trúc crawler và discovery flow

Sơ đồ này mô tả ranh giới giữa Admin Next.js, package importer, worker, PostgreSQL và Redis. Phần dưới giải thích chính xác vì sao cùng một reducer action ANALYSIS_SUCCEEDED được dùng cho cả khôi phục dữ liệu cũ và discovery vừa hoàn tất.

Codebase snapshot: 03/08/2026

01 / Tổng thể

Luồng dữ liệu theo layer

Redis không nằm giữa server và PostgreSQL. Nó là hạ tầng điều phối công việc nền; PostgreSQL vẫn là nguồn dữ liệu chuẩn.

02 / Khi mở màn hình

Khôi phục discovery gần nhất

Effect này không phân tích URL mới. Nó tìm import job gần nhất của uploader hiện tại và phục hồi workflow nếu có.

useEffect(() => {
    let active = true;

    getLatestImportDiscoveryAction().then((result) => {
        if (!active || !result.ok || !result.data) return;

        dispatch({
            type: "ANALYSIS_SUCCEEDED",
            data: result.data,
        });
    });

    return () => {
        active = false;
    };
}, []);
Điều kiệnKết quả
active === falseReturn, component đã unmount
result.ok === falseReturn, action thất bại
result.data không tồn tạiReturn, không có lịch sử để khôi phục
Cả ba điều kiện trên đều không xảy raDispatch và hydrate reducer state
Điểm cần làm rõ: Khi không có data cũ, callback đã dừng ở từ khóa return. Dòng dispatch phía dưới không chạy. Tên ANALYSIS_SUCCEEDED chỉ mô tả trạng thái cuối cùng là “đã có kết quả phân tích hợp lệ”, không khẳng định kết quả vừa được tạo trong lần mount này.

Call chain

Từ Client Component tới PostgreSQL.

  1. Client effectGọi getLatestImportDiscoveryAction() khi mount.
  2. Server ActionChuẩn hóa kết quả thành { ok, data, error }.
  3. DALLấy actor hiện tại và kiểm tra quyền uploader/admin.
  4. Application serviceGọi findLatestImportJob(actor.id).
  5. RepositoryĐọc import job mới nhất và dựng DTO cho UI.

Reducer phục hồi gì?

Không chỉ metadata của truyện.

  1. Discovery resultURL nguồn, story metadata, catalog summary, edition.
  2. Import configurationMode, range, target story và concurrency đã chọn.
  3. Job lifecycleStatus và active job id nếu job còn đang chạy.
  4. Screen positionCó thể chuyển thẳng tới progress khi job đang queued/running/review.

03 / Khi bấm Phân tích nguồn

Discovery mới

Đây mới là flow tạo yêu cầu phân tích URL. Nó có thể trả kết quả trực tiếp hoặc tạo job nền rồi để UI polling.

Nhánh trả kết quả ngay

Khi server đã có discovery dùng lại được.

  1. Validate URLSai domain/path thì dispatch ANALYSIS_FAILED.
  2. START_ANALYSISUI chuyển sang trạng thái đang phân tích.
  3. Server ActionGọi discoverStorySourceAction với client request id.
  4. Có discovery trong responseDispatch ANALYSIS_SUCCEEDED ngay.

Nhánh chạy qua worker

Khi discovery cần xử lý nền.

  1. Queue jobServer lưu job và đẩy job id vào BullMQ/Redis.
  2. DISCOVERY_QUEUEDClient giữ activeJobId và bắt đầu polling.
  3. Worker xử lýLấy metadata, catalog summary rồi persist progress vào PostgreSQL.
  4. Polling thấy DRAFTClient gọi lại latest discovery và dispatch ANALYSIS_SUCCEEDED.

PostgreSQL giữ dữ liệu chuẩn

  • Import source, job, story draft và chapter draft.
  • Progress bền vững để reload UI vẫn phục hồi được.
  • Kết quả cuối và error code có thể audit.

Redis điều phối công việc tạm thời

  • Queue job và phân phối cho worker.
  • Retry, backoff, lock và concurrency.
  • Cache ngắn hạn tình trạng origin khỏe/yếu.

Tài liệu được tạo từ code hiện tại. Nếu action reducer được đổi tên, nên cân nhắc RESTORE_DISCOVERY cho mount flow và giữ ANALYSIS_SUCCEEDED cho discovery mới để intent dễ đọc hơn. Đây là cải thiện naming, không phải lỗi behavior.
